# OMR 프로젝트 포트폴리오 전략

## 1. 포지셔닝 전략

이 프로젝트는 "OMR 판독 프로그램을 만들었다"가 아니라 "판독 이후 사용자가 결과를 이해하고 수정하는 흐름까지 설계했다"로 포지셔닝하는 것이 맞다.

- 프로젝트의 본질: 스캔 이미지 분석 도구
- 포트폴리오의 핵심 메시지: 판독 기능보다 결과 확인과 오류 수정 경험을 더 중요하게 봤다
- 채용 직무 연결점: 기능 구현 경험을 바탕으로 사용자 혼선, 예외 처리, 운영 흐름, 가이드 문서화를 함께 고민한 사람으로 보이게 한다
- 문서 톤: 기술 설명은 필요한 만큼만 쓰고, 왜 이 흐름을 정리하려 했는지에 초점을 둔다

이 포트폴리오는 개발 포트폴리오가 아니라 서비스 기획/운영 관점의 프로젝트 문서여야 한다. 따라서 기능 목록보다 다음 질문에 답하는 구조가 더 중요하다.

- 사용자는 어디에서 막히는가
- 그 혼선을 어떤 화면과 흐름으로 줄이려 했는가
- 나는 어떤 기준으로 예외를 나누고 수정 경험을 설계했는가
- 이 경험이 협업형 서비스 운영 업무와 어떻게 연결되는가

## 2. 6페이지 구성안

| 페이지 | 제목 | 핵심 메시지 |
| --- | --- | --- |
| 1 | 판독 기능보다 흐름을 먼저 설계한 OMR 프로그램 | 단순 개발 결과물이 아니라 결과 확인과 오류 수정 경험을 다룬 프로젝트다 |
| 2 | 기능이 끝나도 사용성은 끝나지 않는다 | 판독 완료 이후 사용자가 무엇을 이해하고 어떻게 수정하는지가 핵심 문제였다 |
| 3 | 맡은 역할: 구현과 흐름 설계를 함께 담당 | 엔진, 화면, 결과 표시, 오류 수정, 예외 기준을 함께 구조화했다 |
| 4 | 스캔 > 판독 > 확인 > 수정 흐름을 다시 설계 | 사용자 여정 단계별로 막히는 지점을 줄이는 방향으로 개선했다 |
| 5 | 결과: 더 잘 읽히는 도구, 더 분명한 운영 흐름 | 수치 대신 구조적 산출물과 학습을 정리한다 |
| 6 | 네이버웍스 서비스 기획/운영과의 연결 | 온보딩, 운영 UX, 예외 처리, 가이드 문서화로 이어지는 경험이다 |

## 3. 페이지별 문구 초안과 레이아웃 가이드

### 1페이지

#### 제목
판독 기능보다 흐름을 먼저 설계한 OMR 프로그램

#### 핵심 메시지
이 프로젝트는 스캔 이미지를 판독하는 프로그램이지만, 더 중요하게 본 지점은 사용자가 결과를 확인하고 오류를 수정하는 과정이었다.

#### 실제 문구 초안
스캔한 OMR 이미지를 분석하고 결과를 저장하는 Python·PyQt 기반 프로그램이다.  
이 프로젝트에서 집중한 지점은 판독 정확도 자체보다, 사용자가 결과를 어떻게 이해하고 어디서 수정해야 하는지를 덜 헷갈리게 만드는 흐름이었다.

판독 도구는 결과만 내보내면 끝나지 않는다.  
실제 사용자는 스캔 이후 어떤 항목이 문제인지 확인하고, 이미지와 결과를 함께 비교하며, 수정이 끝났는지 다시 판단해야 한다.  
이 프로젝트는 그 과정을 하나의 작업 흐름으로 정리하려는 시도였다.

#### 레이아웃 가이드
- 상단: 프로젝트명, 한 줄 소개, 지원 직무 라벨
- 중단: 프로젝트 성격을 설명하는 짧은 리드 문장
- 하단: 핵심 키워드 3개 카드
- 카드 예시: `스캔-판독-검토-수정`, `결과 이해성`, `예외 처리와 수정 동선`

### 2페이지

#### 제목
기능이 끝나도 사용성은 끝나지 않는다

#### 핵심 메시지
OMR 프로그램에서 진짜 혼선은 판독 후에 발생한다. 무엇이 정상인지, 무엇을 다시 봐야 하는지, 수정 후 상태가 어떻게 반영되는지가 명확해야 한다.

#### 실제 문구 초안
기존의 OMR 작업은 "판독이 된다"와 "업무가 끝난다"가 같지 않다.  
결과가 출력되어도 사용자는 다음 문제를 바로 마주한다.

- 어떤 건이 정상이고 어떤 건이 다시 확인 대상인지 한눈에 구분되는가
- 오류가 난 이유를 사용자가 이해할 수 있는가
- 이미지와 판독 결과를 함께 보며 수정할 수 있는가
- 수정 이후 상태가 다시 화면에 반영되는가

기능 구현만으로는 사용성이 완성되지 않는다고 봤다.  
특히 결과 확인과 오류 수정이 매끄럽지 않으면, 판독 정확도가 높아도 실제 업무에서는 다시 시간을 쓰게 된다.  
그래서 이 프로젝트를 "판독 엔진"이 아니라 "판독 이후를 끝까지 처리하는 도구"로 보려고 했다.

#### 레이아웃 가이드
- 좌측: 문제 정의 문장 1개
- 우측: 사용자가 느끼는 혼선 4개 박스
- 하단: "왜 결과 확인과 오류 수정이 중요한가" 요약 카드

### 3페이지

#### 제목
맡은 역할: 구현과 흐름 설계를 함께 담당

#### 핵심 메시지
개발만 한 것이 아니라, 사용자 혼선을 줄이기 위한 구조와 기준을 직접 정리했다.

#### 실제 문구 초안
이 프로젝트에서 나는 판독 엔진과 화면 흐름을 함께 점검했다.  
어떤 오류를 검토 대상으로 묶을지, 결과를 어떤 상태값으로 보여줄지, 수정 동선을 어떻게 단순하게 만들지 같은 기준을 직접 정리했다.

주요 역할은 다음과 같다.

- 스캔 이미지 분석과 결과 저장 구조 점검
- 스캔 세션과 시험실 단위로 결과를 묶어 보는 화면 흐름 정리
- 결과 그리드에서 정상, 오류, 미점검, 수정 완료 상태를 구분해 표시
- 오류 검토 큐를 구성하고, 이미지와 판독 결과를 함께 보는 수정 화면 설계
- 수정 결과를 저장하고 다시 검토 상태에 반영하는 기준 정리
- 수동 수정 이력과 예외 메시지를 남겨 이후 확인이 가능하도록 구조화

이 역할을 통해 나는 단순히 기능을 붙인 사람이 아니라, 사용자가 다음 행동을 판단할 수 있도록 문제를 구조화한 사람이라는 점을 보여주고 싶다.

#### 레이아웃 가이드
- 상단: 역할 요약 문장
- 중단: `직접 다룬 범위`와 `판단 기준` 2열 구성
- 하단: 구현 범위를 보여주는 태그형 요소
- 태그 예시: `결과 표시`, `오류 큐`, `수정 로그`, `예외 메시지`, `검토 상태`

### 4페이지

#### 제목
스캔 > 판독 > 확인 > 수정 흐름을 다시 설계

#### 핵심 메시지
핵심은 오류를 완전히 없애는 것이 아니라, 오류가 생겼을 때 사용자가 덜 막히도록 흐름을 단순하게 만드는 일이었다.

#### 실제 문구 초안
프로젝트를 설계할 때는 기능 목록보다 사용자 여정을 먼저 봤다.

1. 스캔  
현재 어떤 시험실을 처리 중인지, 몇 건이 들어왔는지, 다음 시험실로 넘어갈지 중단할지 같은 작업 상태가 먼저 보여야 했다.

2. 판독  
판독 결과는 단순 성공/실패가 아니라, 어떤 이유로 재검토가 필요한지 드러나야 했다.  
그래서 오류 메시지와 검토 상태를 분리해 관리하려 했다.

3. 결과 확인  
사용자는 전체 결과를 한 건씩 보는 것이 아니라, 시험실 단위와 결과 목록을 오가며 확인한다.  
그래서 요약 영역과 결과 그리드를 함께 두고, 어느 건이 미점검인지 바로 찾을 수 있도록 정리했다.

4. 오류 수정  
수정 화면에서는 이미지와 결과를 따로 보게 하면 판단 비용이 커진다.  
정렬된 이미지, 판독 결과, 이전/다음 이동, 저장 후 다음 항목으로 넘어가는 동선을 한 화면에 묶어 검토 흐름을 줄이려 했다.

이 과정에서 중요하게 본 것은 "정확한 판독"보다 "수정 가능한 판독"이었다.  
사용자는 완벽한 자동화를 기대하기보다, 문제가 생겼을 때 빠르게 이해하고 고칠 수 있는 도구를 더 필요로 한다고 봤다.

#### 레이아웃 가이드
- 중앙 메인: 4단계 흐름도
- 각 단계 안에 `사용자 질문`과 `개선 포인트`를 한 줄씩 배치
- 우측 또는 하단: 설계 원칙 카드
- 원칙 예시: `상태를 분리해서 보여주기`, `이미지와 결과를 함께 보기`, `수정 후 다음 행동이 분명한 화면`

### 5페이지

#### 제목
결과: 더 잘 읽히는 도구, 더 분명한 운영 흐름

#### 핵심 메시지
정량 성과를 과장하지 않고, 이 프로젝트를 통해 무엇이 구조적으로 정리되었는지와 무엇을 배웠는지를 담백하게 보여준다.

#### 실제 문구 초안
이 프로젝트는 외부 운영 지표나 대규모 사용자 수치를 제시할 수 있는 성격의 작업은 아니다.  
그래서 결과는 숫자보다 구조적 변화와 학습 중심으로 정리했다.

프로젝트를 통해 정리한 산출물은 다음과 같다.

- 오류 건만 다시 확인할 수 있는 검토 큐
- 정상 상태와 수정 완료 상태를 나누어 보는 결과 구조
- 수동 수정 내용을 남기는 이력 기록 방식
- 기존 데이터를 다시 읽어 오류 표기를 갱신하는 재확인 흐름
- 시험실 단위로 현재 작업량을 파악하는 요약 구조

이 경험을 통해 서비스는 기능만으로 완성되지 않는다는 점을 더 분명하게 배웠다.  
작은 문구, 버튼의 위치, 저장 이후 다음 행동, 예외 메시지의 기준처럼 사소해 보이는 요소가 실제 사용 경험을 크게 바꾼다.  
이후에는 화면 하나보다 사용자 경험의 전체 흐름을 먼저 보려고 하게 되었다.

#### 레이아웃 가이드
- 상단: 결과 요약 문장
- 중단: `정리된 산출물` 카드 4~5개
- 하단: `배운 점` 문단 2개
- 작은 주석으로 `허위 수치 없이 구조 중심으로 정리` 문구 배치

### 6페이지

#### 제목
네이버웍스 서비스 기획/운영과의 연결

#### 핵심 메시지
사용자가 헷갈리지 않게 만드는 경험을 설계한 점이 협업형 업무 서비스의 기획/운영 업무와 자연스럽게 연결된다.

#### 실제 문구 초안
네이버웍스 서비스 기획/운영 직무에서도 중요한 일은 비슷하다고 생각한다.  
기능을 추가하는 것보다 먼저, 사용자가 어디에서 멈추는지 정의하고, 예외 상황을 설명 가능한 기준으로 정리하고, 처음 쓰는 사람도 다음 행동을 이해할 수 있게 만드는 일이다.

이 프로젝트 경험은 다음 업무와 연결될 수 있다.

- 온보딩 UX 개선: 처음 사용하는 사용자도 현재 상태와 다음 행동을 이해할 수 있게 만드는 일
- 운영 화면 개선: 결과 목록, 상태값, 예외 항목을 한눈에 파악할 수 있는 관리 화면 설계
- 고객지원 흐름 정리: 오류 유형과 수정 기준을 문서화하고 반복 문의를 줄이는 구조 만들기
- 서비스 운영 문서화: 기능 설명보다 실제 사용 흐름과 예외 처리 기준 중심으로 안내 문서를 정리하는 일

나는 이 프로젝트를 통해 기술을 구현하는 경험과, 그 기능이 사용자에게 어떻게 읽히는지를 함께 보는 관점을 쌓았다.  
네이버웍스에서도 사용자가 헷갈리지 않도록 흐름을 정리하고, 운영 가능한 기준으로 문서화하는 역할에 강점을 발휘할 수 있다고 본다.

#### 레이아웃 가이드
- 상단: 직무 연결 한 줄 메시지
- 중단: 직무 연결 카드 4개
- 하단: 마지막 정리 문장
- 마지막 문장은 자기소개서처럼 감정적으로 쓰지 말고, 역할 적합성을 차분하게 정리

## 4. 채용 담당자 시점 강점 / 보완점

### 강점

- 기능 구현 경험이 실제 UI와 데이터 흐름 설계로 이어져 있다
- 오류 수정 경험을 별도 문제로 정의한 점이 서비스 기획 관점과 잘 맞는다
- 기술 설명에 머물지 않고 사용자 혼선과 다음 행동을 중심으로 사고했다
- 허위 수치 없이도 설득할 수 있는 구조를 만들 수 있다

### 보완점

- 실제 사용자 인터뷰나 관찰 기록이 추가되면 설득력이 더 높아질 수 있다
- 경쟁 서비스 분석 또는 업무용 SaaS 화면 비교가 1장 정도 더 있으면 네이버웍스 직무 연결성이 더 강해진다
- 예외 처리 기준을 문서화한 샘플이 함께 있으면 운영 직무 적합성이 더 분명해진다

## 5. 제출용 편집 원칙

- 페이지당 메시지는 1개만 남긴다
- 본문은 길게 늘어놓지 말고 카드, 단계도, 요약 박스로 끊는다
- 포인트 컬러는 1개만 사용하고 나머지는 흑백 계열로 정리한다
- PDF 저장 시 배경 그래픽을 켜고 A4 세로 기준으로 출력한다
- 문장은 "잘했다"보다 "왜 그렇게 설계했는가"에 집중한다
